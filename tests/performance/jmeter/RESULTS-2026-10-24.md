# 真实拼团交易链路压测结果（2026-10-24）

后续已开始第一轮性能优化；本文保留优化前基线数据。新版本的代码和脚本已准备，实际回归与压测待用户恢复，见 [优化准备说明](OPTIMIZATION-2026-10-24.md)。

本次测试针对 group-buy-travel 的真实下单、结算、成团与 Kafka 消费链路。五轮性能测试与六类并发正确性检查全部通过。50 并发三轮中位数：成功下单 **33.511 单/s**、下单 **P95 1599 ms**、下单 P99 2578 ms。

## 测试条件与口径

- 正式运行：2026-10-24T16:28:14.098700+08:00 至 2026-10-24T16:34:52.993730+08:00；结果目录 [real-trade-20261024-162814](results/real-trade-20261024-162814/)。
- 本机 Windows 10，AMD Ryzen 5 4500U（6 核/6 线程），系统可用总内存约 15.4 GiB。JMeter、应用和 Docker 依赖在同一台电脑运行，期间有其他程序占用资源。
- JDK 17、JMeter 5.6.3；MySQL 8.0.32、Redis 7.4、Kafka 3.9.1 均为专用容器。业务请求发到 127.0.0.1:38091。
- 应用堆 64–320 MiB、JMeter 堆 32–128 MiB，二者均设置 ActiveProcessorCount=2；该参数用于 JVM 的处理器计数，并未限制操作系统 CPU 调度。
- HTTP 工作线程 20，Hikari 最大连接数 10。测试启动参数、镜像配置与硬件快照均已保存。
- 10、25、50、50、50 个并发交易用户；每轮 60 秒，前 15 秒预热，固定测量窗口 45 秒，无思考时间。每个用户顺序执行团长下单、团长结算、成员参团下单、成员结算；每个四步流程产生两个订单和一个双人团。
- 成功下单 TPS 仅统计两个创建订单接口的成功请求，不叠加结算接口或事务样本。P95/P99 是成功下单 HTTP 请求的最近秩百分位，按请求开始时间归属测量窗口。
- 支付由测试发送结算通知驱动；Kafka 验证到 broker ACK 与消费端 Redis 幂等标记。外部支付网关、景区出票接口尚未接入本次测试。四步 HTTP 流程的计时不包含异步消息消费延迟。
- 吞吐和延迟剔除预热；最终数据核验包含预热和到期前已开始、随后完成的交易。

本次提供修复正确性后的基线，没有可比的优化前性能数据，因此不产生吞吐提升百分比。此前助手对话链路的 73.4% / 37.7% 不适用于本项目。

## 运行中修复的问题与证据

1. 应用入口丢弃命令行参数：SpringApplication.run 传入 args，专用依赖与端口配置才生效。首次仅做启动检查即发现，无交易请求进入开发环境。证据：results/real-trade-20261024-161312/application.log。
2. 未配置标签范围时下单空指针：isVisible/isEnable 对空范围返回默认允许。原始异常：results/before-fixes-20261024-161820/application.log。
3. 防重和日历规则误将迭代责任链当作递归调用，读取空返回：改由请求上下文记录实际占用的资源，规则或落库失败时统一补偿，避免误释放其他请求的占用。原始异常：results/real-trade-20261024-162058/application.log。
4. 成团 SQL 状态值由 2 修正为 COMPLETE=1；结算明细更新增加 status=0 条件，防止重复回调多次累计。
5. 同团不同订单同时结算时读到旧计数：在事务内按当前 complete_count=target_count 条件完成状态转换，仅转换成功的请求生成通知。修复前 20 单全部支付、10 个团队均停在状态 0 且未生成通知；证据：results/real-trade-20261024-162426/correctness.json。修复后同场景全部通过。

修复后 JDK 17 离线 Maven 打包成功（跳过原项目测试），实际业务验证来自本次真实 HTTP 回归和压测。最后一次构建日志：results/build-concurrent-settlement-fix.log。

# 真实拼团交易：请求延迟诊断

本文记录早期诊断阶段；后续性能配置调整与 100 QPS 实验见 [后续报告](QPS100-2026-10-24.md)，当前配置以该报告及实际配置文件为准。

## 目标与口径

定位 50 并发下单接口约 1 秒的延迟，尝试将成功下单 P95 降到 500 ms 以内，同时观察成功 QPS。
每轮 60 秒，前 15 秒预热；每次双人团包含下单、结算、入团下单、结算四次真实 HTTP 请求。
使用真实 MySQL、Redis 和 Kafka；支付回调由脚本构造，未调用外部支付或景区出票服务。

## 已完成的诊断

逐请求计时默认关闭，启用参数为 `--trade.trace.enabled=true`。
`Server-Timing` 响应头由 JMeter 保存到同一行 `serverTiming`，包括：

- 未支付订单查询、团队进度查询、营销试算和交易规则校验。
- 事务开始、业务体和提交/回滚完成。
- 获取数据库连接、JDBC 执行、会话状态调用、commit/rollback、连接归还。
- 交易路径的同步 Redis 调用及营销查询线程的排队/执行。

JDBC 执行计时包含驱动、网络往返和线程调度，不等同于 MySQL 服务端 SQL 执行时间。
HTTP 总耗时减去应用计时还包含进入过滤器前的排队、网络、响应序列化和客户端调度，不能全部称为 Tomcat 队列时间。
事务和业务阶段包含 JDBC/Redis 子阶段；两个营销查询可以并行，不能直接相加全部阶段或各阶段 P95。
诊断没有逐请求日志，也不在响应头记录用户信息、订单号或 SQL 文本。

## 第一轮诊断结果

归档：`results/request-latency-20261024-222539/comparison-20261024-222539`。
50 并发、HTTP 工作线程 20、Hikari 最大连接 10、通知批处理关闭。
成功下单 QPS **38.889**，P95 **1171 ms**；本轮全部 **2144** 张订单通过库存、结算、成团和 Kafka 核验。
整机平均 CPU **88.53%**，最低可用内存 **1506.7 MiB**。
这是一轮诊断，不能作为三轮对照的中位数。

| 指标 | 所有成功下单的平均值 ms | 最慢约 5% 下单的平均值 ms |
| --- | ---: | ---: |
| JMeter HTTP 总耗时 | 736.101 | 1432.784 |
| 应用计时区间 | 347.644 | 730.940 |
| 应用区间以外 | 388.457 | 701.844 |
| 获取连接累计耗时（嵌套阶段） | 211.712 | 481.762 |
| JDBC 执行累计耗时（嵌套阶段） | 40.895 | 74.196 |

主要可疑点是取连接和 HTTP 请求进入应用前后的等待，而不是脚本固定睡眠或单条慢 SQL。
JMeter 计划没有逐请求 Timer/sleep；5 秒 ramp-up 只用于起压。
MySQL 侧本轮业务 SQL 平均约 0.3–2.9 ms，COMMIT 平均约 62.45 ms。
每张订单仍约有 6 次 `transaction_read_only` 查询，但该 SQL 在服务端平均仅约 0.27 ms，需要结合客户端往返成本评价。

## 已筛选、待重复对照的优化组合

- HTTP 工作线程从 20 调整为 50，与压测请求并发匹配。
- Hikari 最大连接从 10 有界增加为 40；20 连接为中间筛选档。
- Connector/J `useLocalSessionState=true`，减少重复读取会话只读状态的数据库往返。
- 两组均保持 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`，通知批处理关闭，数据/索引/JVM 参数一致。

`useLocalSessionState` 要求通过 JDBC 接口管理事务状态。当前应用未通过 SQL 或存储过程直接修改 autocommit、隔离级别或只读状态。
先对优化组执行正确性预检和单轮试验，再按 ABBAAB 各三轮对照；保留所有结果。

```powershell
python tests/performance/jmeter/compare_request_latency.py --diagnose-only
python tests/performance/jmeter/compare_request_latency.py --optimized-pilot
python tests/performance/jmeter/compare_request_latency.py
```

每次执行保留独立目录和应用 SHA256；原始 JTL、分段分析、SQL 增量、事务指标和资源采样一并保留。
初始可用内存至少 2048 MiB，容器启动后的阶段门槛 1024 MiB，负载运行时低内存保护仍生效。
所有变更只作用于专用测试环境，不停止开发容器。

来源：[JMeter elapsed time 定义](https://jmeter.apache.org/usermanual/glossary.html)、[Connector/J 会话状态配置](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-performance-extensions.html)、[8.0.22 驱动实际实现](https://github.com/mysql/mysql-connector-j/blob/8.0.22/src/main/user-impl/java/com/mysql/cj/jdbc/ConnectionImpl.java)。

### 耗时变化

| 下单请求的平均耗时 ms | 原配置 | 20 连接 | 40 连接 |
| --- | ---: | ---: | ---: |
| HTTP 总耗时 | 736.101 | 555.112 | 421.919 |
| 应用区间以外 | 388.457 | 1.780 | 4.381 |
| 获取连接累计耗时（嵌套） | 211.712 | 369.137 | 76.434 |
| commit（嵌套） | 62.444 | 81.677 | 148.553 |
| JDBC 执行（嵌套） | 40.895 | 55.850 | 82.704 |
| Redis（嵌套） | 22.795 | 31.758 | 65.622 |

增加 HTTP 工作线程后，客户端减去应用区间的差值从约 388 ms 降至约 2–4 ms，支持原配置存在明显的服务入口排队。
只增加到 20 个连接时，排队转移到连接池；运行中观测到 20 个连接全部占用、29 个取连接等待。
增加到 40 后取连接累计耗时减少，但 COMMIT、SQL 往返及 Redis 耗时上升，且整机平均 CPU 94.06%，说明继续扩容不能保证继续改善延迟。
`transaction_read_only` 在原配置存在（12874 次），两个优化档的 SQL 增量中均消失，证明本地会话状态配置生效。
事务/Redis/JDBC 阶段包含线程调度等待，不能仅凭客户端计时把上升全部归因于数据库或 Redis 服务端。

## 可启用配置与复测

新增 `application-performance.yml`，以 `--spring.profiles.active=dev,performance` 启用 50 HTTP / 40 连接及本地会话状态配置。
该配置沿用外部连接地址，诊断和通知批处理默认关闭；它是本次单实例筛选得到的候选配置，尚未经三轮验证。
多个实例共享数据库时，需要重新分配总连接预算。本次专用 MySQL `max_connections=60`。
压测脚本仍逐组显式传参，并在升压前校验实际 Hikari 最大连接数，避免加载错配置。

复测前需释放足够内存，然后执行 `python tests/performance/jmeter/compare_request_latency.py`，按 ABBAAB 完成各三轮，再报告中位数与相对变化。

# 第一轮真实拼团性能优化对照结果（2026-10-24）

本轮已完成两版真实交易回归及六轮 50 并发对照。交易正确性全部通过，但未验证到整体性能提升：优化版成功下单吞吐量的三轮中位数为 45.533 单/s，基线为 47.822 单/s，下降 4.79%；下单 P95 为 978 ms，基线为 830 ms，上升 17.83%。这组结果不能表述为“吞吐提升、延迟降低”。

运行时间：2026-10-24 18:08:09—18:19:21（Asia/Shanghai）。

## 对照方式与统计口径

- 测试对象为真实拼团交易：团长下单 → 团长结算 → 团员参团下单 → 团员结算 → 成团通知落库 → Kafka 发送确认及消费标记核验。
- MySQL 订单、Redis 库存、Kafka 均为实际组件；支付由测试回调驱动，未接外部支付或景区出票服务。
- 单热点票种、二人团、固定游玩日期、充足库存，使用不同用户和外部订单号。此模型验证创建新团和参团，不是大量用户争抢同一个团的吞吐模型；最后席位竞争另由正确性用例覆盖。
- 每轮 50 个虚拟用户、60 秒运行，前 15 秒为预热，固定 45 秒计量；按“基线、优化、优化、基线、基线、优化”交替运行。
- 每阶段恢复专用对照库的交易种子、清空已备份的专用测试 Redis、使用新 Kafka 主题；只有优化版执行两条新增订单索引。未改动原业务库。
- 两版均使用 JDK 17、应用最大堆 320 MiB、JMeter 最大堆 128 MiB、Tomcat 20 工作线程、Hikari 最大 10 连接；MySQL innodb_flush_log_at_trx_commit=1、sync_binlog=1、buffer pool=64 MiB。
- 吞吐量仅统计成功创建订单，不把结算、HTTP 子请求或事务样本累加成“订单”。完整成团流程包含两个订单及两个结算 HTTP 请求；其时延不包含异步 Kafka 消费等待。
- 各类 TPS 按请求/流程开始时间落入计量窗口统计，P95/P99 为该窗口成功样本的最近秩分位数；最终数据是每版三轮指标的中位数，不是合并全部样本后的分位数。

## 正确性与独立复核

- 两版各自通过六类真实并发用例：重复创建、重复结算、日历库存最后五张、不同日期库存隔离、团队最后一个席位、不同成员同时结算。用例中的重复/库存不足拒绝属于预期结果。
- 六轮负载共完成 15,860 个已支付订单、7,930 个完整团，31,720 次业务 HTTP 请求的业务码均为 0000；包含预热及收尾，未将冒烟和独立正确性用例计入这些总数。
- 每轮均核对订单唯一性、支付数量、Redis 占用、团队人数和状态、通知任务、Kafka 发送确认、消费标记；未发现重复订单、超卖、漏成团或遗留失败通知。
- 独立重读六份原始 JTL，重算 TPS/P95/P99，并与结果 JSON 及数据库/消息核验交叉核对，全部一致。

资源采样涵盖 JMeter 启动、预热和负载，不单独裁去预热。两版均观察到 10 个连接全部占用；等待连接最多 14 个。Actuator 指标采用 300 ms 超时，部分采集超时，连接池数值是已成功采样的观测值，不能视为完整时序峰值。

测试运行于同一台 Ryzen 5 4500U、6 核 6 线程、约 15.4 GiB 内存的 Windows 机器，JMeter、应用、Docker 及其他程序共享资源。应用与 JMeter 进程 CPU 时间折算合计约占整机 25%–26%，整机 CPU 均值约 84%–92%。结果反映当前本机环境，不能作为服务的最大并发容量。

综合判断：缓存和团队查询索引确实减少了查询工作量，整体性能却仍受事务提交、通知状态写入及连接等待影响。本轮未单独采集 redo/binlog 刷盘、磁盘延迟与完整锁等待分解，不能把提交耗时直接归因于磁盘，也不能将中位数下降完全归因于某一项代码改动。三轮样本和同机资源波动不足以作统计显著性结论。

## 后续优先项

1. 给下单和结算增加事务阶段与连接持有时长观测，并同步采集 MySQL 日志/文件 I/O 和锁等待，先细分提交等待来源。
2. 评估有界合并通知状态回写，减少独立提交；保留通知任务落库、失败重试和消费者幂等，继续用真实消息与数据核验验收。
3. 对两条索引和通知线程池参数分别做对照，确认单项收益及写入成本；本轮两种版本包含多项改动，尚未拆分各项影响。

两版 MySQL 持久性参数保持一致，本轮性能负载固定为 50 并发。

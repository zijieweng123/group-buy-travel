# 真实拼团交易成功下单 QPS 100+ 优化

## 口径与改动

目标是在 50 并发下获得 100+ 成功下单 QPS，并同时观察成功下单 P95 与交易一致性。
每轮 60 秒，剔除前 15 秒预热；下单与结算分别统计，完整流程父样本不重复计入 HTTP QPS。
MySQL、Redis、Kafka 均为真实依赖，支付回调由脚本构造，未调用外部支付/景区出票。

本轮固定 HTTP 工作线程 50、Hikari 最大连接 40、Connector/J 本地会话状态开启。
同构建对照通过功能开关选择以下代码，原路径仍保留：

1. 下单规则将活动状态/时段、用户参与次数、选定日期库存容量合并为一次 SQL，之前为三次。
2. 结算规则将未支付订单和对应团队合并为一次 SQL，之前为两次。写入事务仍通过数据库条件更新防止重复结算或重复成团。
3. 所有读取仅在当前请求的规则 Context 内复用，未缓存动态库存、限购次数或活动状态。
4. 候选 Redis Lua 将请求防重和日期库存占用合并成一次原子执行。不同 HTTP 请求不能共用占位；同一次调用的网络重试使用固定调用令牌，避免重复增加库存占用。
5. 只有成功预占才将两项资源记录到 Context，数据库失败沿用原补偿路径释放库存与请求锁。

原子预占默认关闭，依赖合并 SQL 提供的新鲜库存容量；当前项目使用独立 Redis。
脚本显式传入所有 Redis keys；如果改用 Cluster，需要让相关 keys 位于同一槽后再启用。
[Redis 脚本原子执行说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)、[Redisson 脚本接口说明](https://redisson.pro/docs/server-side-scripting/)。

## 配置筛选结果

- 仅合并 SQL：**98.133 成功下单 QPS，P95 447 ms**，5306 张订单全部通过核验。平均 CPU 93.24%，最低可用内存 1485.5 MiB。
- 合并 SQL 加通知状态批处理：**97.244 QPS，P95 478 ms**。平均 CPU 96.99%，最低可用内存 1107.1 MiB；未证明优于上一档，保持通知批处理默认关闭。

两档均通过 12 项真实存储预检。上述是不同时间各一次的筛选结果，不能据此声称正式优化比例。
第一档已观察到成功下单 P95 低于 500 ms，QPS 仍略低于 100，需要继续验证。
第一档每个下单请求的 JDBC 执行次数约 5.5 次（之前约 7.5 次），获取连接约 4.5 次（之前约 6.5 次）。

原始数据位于 `results/qps100-20261024-225811`，每次运行保留单独 comparison 目录、构建 SHA256、源码/脚本归档、JTL、逐请求分析和一致性结果。

## 验证方式

Java 回归覆盖合并查询结果映射、限购、缺失活动、过期结算、功能关闭回退，以及原子预占资源登记、错误拒绝、数据库写入失败补偿。
真实预检包括既有库存/并发/通知 8 项，新增限购、日期停售、活动状态/时段/缺失 ID、团队结算过期 4 项；原子脚本另检查同令牌重放、不同请求防重、库存耗尽、租期和错误前无部分写入。

```powershell
# 只合并 SQL 的单轮筛选
python tests/performance/jmeter/compare_trade_qps.py --pilot
# SQL 加 Redis 原子预占的单轮筛选
python tests/performance/jmeter/compare_trade_qps.py --pilot --atomic-reservation
# 同构建、相同容量，按 ABBAAB 各三轮正式对照
python tests/performance/jmeter/compare_trade_qps.py --atomic-reservation
```

两组均保持 `innodb_flush_log_at_trx_commit=1` 与 `sync_binlog=1`，不放宽订单同步提交和业务断言。
启动前可用内存门槛仍为 2048 MiB，运行期间低内存保护仍生效。

首次原子预占启动曾因可用内存 1979 MiB 低于门槛而拦截，没有发出该次负载；后续已完成真实验证，结果见下文。

## 后续筛选与瓶颈证据

- Redis 原子预占曾达到 106.644 QPS、P95 418 ms，属于单轮筛选。
- 服务端预编译和缓存试验为 76.111 QPS、P95 568 ms；实际记录 46687 次执行、564 次准备、581 条打开语句，配置生效且发生复用，但未证明整体收益，最终配置关闭该选项。缓存试验每连接上限 64、最大 SQL 长度 2048，元数据缓存上限 64。
- 跳过关闭 INFO 日志时的 JSON 序列化，并调到 50 个数据库连接后，单轮为 93.044 QPS、P95 446 ms，取连接平均累计约 5.347 ms。
- 该轮结算平均连接获取次数 2.277，超过合并读取加写事务预期的 2 次；结合 CallerRunsPolicy，说明部分通知回写在请求线程中执行。结算应用平均耗时 251.356 ms，规则及事务阶段合计约 199 ms，额外耗时约 52 ms，包含同步派发通知及其他开销。
- 通知线程调整到 12 后，单轮为 88.889 QPS、P95 513 ms；结算 P95 降到 354 ms，派发阶段平均 0.007 ms，连接获取回到 2 次。整体吞吐仍未达标，继续以批量回写减少独立通知提交。

预编译缓存参数参考 [HikariCP 官方 MySQL 配置说明](https://github.com/brettwooldridge/HikariCP/wiki/MySQL-Configuration)、[Connector/J 缓存参数](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-performance-extensions.html)；最终是否采用取决于本项目实测。

## 2026-10-25 最终组合三轮验证

固定组合：50 并发用户、50 HTTP 工作线程、Hikari 最大连接 50、通知线程 12、通知队列容量 128；启用合并 SQL、Redis 原子预占和通知状态批量回写。预编译缓存关闭。
通知状态队列容量 1024、单批最多 32 条，100 ms 定时触发刷新；100 ms 是触发周期，不是数据库确认延迟上限。
订单与结算事务仍同步提交，批量回写仅处理 broker ACK 后的通知成功状态。
每轮 60 秒，前 15 秒预热，同一最终构建重复三轮。

| 轮次 | 成功下单 QPS | 下单 P95 ms | 成功结算 QPS | 结算 P95 ms | 全量订单 | 完成团 | 平均 CPU | 最低可用内存 MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 102.467 | 414 | 102.644 | 317 | 5450 | 2725 | 96.74% | 1820.0 |
| 2 | 108.400 | 421 | 108.667 | 316 | 5698 | 2849 | 91.64% | 1818.5 |
| 3 | 106.556 | 437 | 106.667 | 339 | 5666 | 2833 | 93.04% | 1952.4 |

三轮中位数：成功下单 **106.556 QPS**，P95 **421 ms**；成功结算 **106.667 QPS**，P95 **317 ms**。三轮下单 QPS 均超过 100、P95 均低于 500 ms。

共 **16814 张订单、8407 个完成团、33628 次业务 HTTP 请求**全部成功，订单唯一性、Redis 日历占用、结算状态、成团计数、Kafka ACK 任务状态和消费幂等标记全部核验通过。预检 **14 项通过**。

本节是最终组合的三轮持续验证，非最终组合与旧版本的 ABBAAB 对照；不将其与历史基线拼接计算严格提升比例。
当前本机仍有较高 CPU 占用，结果代表该测试环境与负载，未测定生产容量上限；支付回调由脚本构造。
